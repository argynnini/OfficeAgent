# `\Map`タグ(および他のSAPI4タグ)の内部挙動について

作成日: 2026-09-09

このプロジェクトで、Windows標準のMicrosoft Agent(`MSAgent64`)にVOICEVOX(SAPIForVOICEVOX経由)や
Windows標準のHaruka音声で喋らせようとした際、「吹き出しの表示文字と発声内容を別々に指定したい」
というニーズから`\Map`タグを調査した記録。

## 前提知識(公式ドキュメントに書かれている内容)

- `\Map="spokentext"="balloontext"\` は、読み上げ音声用のテキストと吹き出し表示用のテキストを
  分離するための、Microsoft Agent独自のタグ(SAPI4形式、いわゆる"スラッシュタグ")。
- Windows Vista以降、Microsoft AgentはSpeak()に渡す文字列の中で、SAPI4形式のスラッシュタグ
  (`\Map\`, `\Pit\`等)とSAPI5形式のXMLタグ(`<PITCH .../>`等)の両方を受け付けるが、
  **SAPI5エンジンを使っている場合はスラッシュタグが無視され、SAPI4エンジンを使っている場合は
  XMLタグが無視される**、という設計になっている。
- サウンドファイルベースの音声出力(録音・合成音声ファイルを直接再生する形式)でも使用できる
  数少ないタグが`Mrk`と`Map`である、とされている。
- Mapタグに含まれるテキストは、吹き出しの文字送り(auto-pace)処理において「1つの単語」として
  扱われる、という記述がある。

## 実機での検証結果

### VOICEVOX(SAPIForVOICEVOX経由、SAPI5エンジン)での検証

`\Map="発声してほしい文言"="吹き出しに出したい文言"\` を含む文字列を`.Speak()`に渡しても、
タグとして解釈されず、吹き出しにも発声にも「吹き出しに出したい文言」の部分がそのまま
（タグ記法込みで、あるいは記法だけ剥がされて）出力される、という挙動だった。

### Windows標準Haruka(SAPI5エンジン)での検証

同じくSAPI5エンジンなので、`\Map`を含むSAPI4形式のタグは無視されるという想定通り、
効果が無かった。念のため、SAPI5形式のXMLタグ(`<sub alias="...">`、`<pron sym="...">`等)も
多数のバリエーションで試したが、いずれも「吹き出し表示≠発声内容」を実現できなかった。
（`<silence>`, `<volume>`, `<rate>`のような単純な音声特性変更タグは正しく機能したので、
XMLタグの解析自体は生きている。テキスト置換・発音指定系のタグだけが機能しなかった。）

## \Mapタグの内部処理について判明したこと

Microsoft Agentサーバー本体(`AgentSvr.exe`)は、`\Map`を含むSAPI4形式のスラッシュタグ全種
(`\emp\`, `\mrk`, `\pau`, `\pit`, `\map`, `\ctx`, `\chr`, `\rst\`, `\spd`, `\vol`, `\lst\`)を
認識するための固定文字列とパース処理を内部に持っている。つまり、`\Map`タグの構文解析ロジック
自体はMicrosoft Agent本体(64bit移植版)に実装されている。

`\Map="spokentext"="balloontext"\` は次のように解析される。

1. `\Map=` の直後が `"..."="..."` の形式かどうかを検証する
2. 1つ目の引用符内の文字列(spokentext)を抽出する
3. 2つ目の引用符内の文字列(balloontext)を抽出する
4. balloontextが空でなければ、内部の「アクションリスト」に
   `種別=Map, サブタイプ=0(balloontext)` として追加する
5. spokentextが空でなければ、同じアクションリストに
   `種別=Map, サブタイプ=1(spokentext)` として、**別のノードとして**追加する
6. 単語区切りカウンタを1つ分だけ進める
   (これが「Mapタグの中身は1つの単語として扱われる」という公式記述の実体)

ここまでは公式ドキュメント通りに正しく動作している。

### 出力生成段階に矛盾がある

このアクションリストは、後続の処理で2種類の文字列（吹き出し表示用の文字列と、
発声用の文字列）を組み立てるために、それぞれ独立に走査される。

内部コードの解析からは「意図とは逆にspokentext側が吹き出しに採用されるのでは」という
仮説が立ったが、これは誤りだった。**実機で確認した実際の挙動は次の通り。**

- **吹き出し表示側: balloontext(2つ目の引数)が正しく表示される**(ドキュメント通り)
- **発声側: spokentext・balloontextとも、Mapタグの中身は常に一切発声されない(無音)**

つまり「\Mapの構文解析、balloontextの吹き出し表示までは正しく動いているが、
spokentextを実際に読み上げる部分だけが機能していない」というのが実態に近い。

### まとめ

`\Map`タグの構文解析・balloontextの吹き出し表示は仕様通りに動く。壊れているのは
「spokentextを実際に発声する」部分だけで、Mapタグの中身(1つ目・2つ目の引数とも)は
常に無音になる。この欠陥はMicrosoft Agent本体(64bit移植版)の実装に内在するものであり、
SAPIForVOICEVOX側やアプリケーション側の工夫では回避できない。

## 実用的な応用: 表示だけ別テキストにする「演出」としての活用

`\Map`単体では「表示はリンゴ・発声はみかん、を完全に両立させる」ことはできない
(spokentextは絶対に発声されないため)。しかし、**「Mapのballoontextで見せたい文字を
出しつつ、その直後の通常テキストで実際に発声させたい文字を続ける」**という組み合わせなら、
「文字が表示された直後に、それとは違う言葉が発声される」という演出として使える。

```
\Map="x"="りんご"\みかん
```
- 吹き出し: 「りんご」(balloontext) + 「みかん」(Map後の通常テキスト、両方残る)
- 発声: 「みかん」だけが聞こえる(Map部分は無音)

### Mapを複数回使う際の重要な制約

1回のSpeak呼び出し内で`\Map`を複数回使うと、**「Map → 通常テキスト → Map」のように、
Mapの後に通常テキストを挟んでから次のMapに入ると、その2番目のMap以降で吹き出し表示の
更新が完全に停止する**という副作用がある(ゼロ幅スペース・半角スペース・`\Rst\`・`\Mrk\`・
`<bookmark>`・ダミーMapのいずれを間に挟んでも回避できないことを確認済み)。

一方、**`\Map`を区切りなく連続させる分には、何個並べても吹き出し表示は壊れない**。
これを利用して、次のように「原文を単語ごとにMapで区切って連続させ、最後にまとめて
読み仮名を1つのテキストとして続ける」形にすると、複数語からなる文でも安定して
「吹き出しには原文、発声には読み仮名」を実現できる。

```
それでは、\Map="x"="Penlight"\\Map="x"="as"\\Map="x"="Takt"\\Map="x"="の紹介と題しまして、"\\Map="x"="Team"\\Map="x"="AHEAD"\\Map="x"="より、"\\Map="x"="Argynnini"\\Map="x"="が発表します。"\ペンライト アズ タクト の紹介と題しまして チーム アヘッド より アルギニーニ が発表します
```

- 吹き出し: 「それでは、Penlight as Takt の紹介と題しまして、Team AHEAD より、Argynnini が発表します。」(各Mapのballoontextが順番に積み上がる)
- 発声: 「それでは、ペンライト アズ タクト の紹介と題しまして チーム アヘッド より アルギニーニ が発表します」(Map部分は全て無音、最後にまとめた読み仮名だけが発声される)

実機での動作を確認済み。各Mapのspokentext(`"x"`部分)はダミーで良い(絶対に発声されない)。

## その他、副次的に判明したこと

- `\Mrk`(SAPI4形式のブックマークタグ)は、内部で`<BOOKMARK MARK="%d"/>`という
  SAPI5 XML形式の文字列に変換されている。SAPI4とSAPI5の橋渡しをMicrosoft Agent自身が
  担っている実装の一端。
- `\rst\`(リセット)タグは、話速・音量・コンテキスト・キャラクタースタイルの4項目を
  まとめてデフォルト値へ戻す、という内部アクションに対応している。
- 音声ファイル(WAV)に単語・音素ラベル情報を付加した`.lwv`(言語的に強化されたサウンド
  ファイル)は、標準WAVE構造に加えて`LIST 'WPMK'`チャンクの中に`WMRK`(単語ラベル)と
  `PMRK`(音素ラベル)という独自サブチャンクを持つ、というファイル形式であることが判明した。
  各エントリは「16バイトのタイミング情報+4バイトの文字列長+文字列本体」という構造。
  `\Map`タグとは別に、こちらは「吹き出し表示≠発声内容」を実現する余地が残っている
  (Speak()にテキストではなく音声ファイルを直接渡す方式で、TTSエンジンを経由しないため)。
  ただし未検証。
